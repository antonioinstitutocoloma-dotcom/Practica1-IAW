# Práctica 1: Servidores, Proxies y Certificados (NimbusDocs)

Para empezar la práctica, lo primero que hice fue usar Docker Compose para poner a trabajar dos servidores juntos: por un lado Apache, que guarda y sirve las webs, y por otro Nginx, que se pone delante para controlar quién entra y gestionar las conexiones seguras. Para arrancar todo sin complicarnos, ejecuté en la terminal el comando docker compose up --build -d, que se encarga de crear las imágenes desde cero y dejarlas funcionando en segundo plano. Justo después, usé docker compose ps para revisar de un vistazo que los dos contenedores estaban encendidos y listos.

A continuación, preparé Apache para que supiera diferenciar mis dos dominios usando Virtual Hosts, separando así la web pública de la interna. Para comprobar que la web pública respondía bien, lancé en la terminal curl -k [https://alpha-docs.net/](https://alpha-docs.net/), usando la opción -k para que no me diera error por usar un certificado de pruebas autofirmado. Además, para proteger la información secreta de la empresa, bloqueé un archivo con claves que creé. Al probarlo con curl -k -I [https://beta-docs.net/credenciales-admin.env](https://beta-docs.net/credenciales-admin.env) (usando el parámetro -I para pedirle al servidor que solo me enseñara la respuesta del encabezado), el sistema me devolvió un aviso de 403 Forbidden, lo que me confirmó que nadie podía ver ni acceder a ese archivo desde fuera.

En el siguiente paso, coloqué a Nginx en la puerta de entrada para recibir las visitas seguras por el puerto 443. Para ello, creé un certificado digital que protege los datos. También puse una redirección automática de tipo 301 para que cualquiera que intentara entrar por la web normal (HTTP) fuera directo a la versión segura (HTTPS), y me aseguré de que Nginx le avisara a Apache de qué dominio exacto estaba pidiendo el usuario. Para comprobar que todo esto funcionaba bien, ejecuté openssl s_client -connect localhost:443 -servername alpha-docs.net, un comando que simula la entrada de un navegador y me confirmó que la conexión se hacía bajo el protocolo moderno TLSv1.3.

Para proteger el servidor de bots y ataques, puse en Nginx cabeceras de seguridad y un limitador de visitas. Esto sirve para que una persona normal pueda navegar sin problemas aunque cargue varias páginas rápido, pero si un programa automático intenta tumbar la web haciendo peticiones sin parar, el servidor lo bloquea. Para probar que esto funciona de verdad, lancé en la terminal un pequeño bucle que hace 25 peticiones seguidas: for i in {1..25}; do curl -k -s -o /dev/null -w "%{http_code}\n" [https://alpha-docs.net/](https://alpha-docs.net/); done. Al ejecutarlo, vi cómo las primeras peticiones daban un código 200 de éxito, pero en cuanto me pasé del límite, empezó a saltar un error 503 Service Temporarily Unavailable, demostrando que el freno de seguridad estaba activo.

Por último, para completar la parte de diagnóstico, explico los dos fallos reales con los que me tropecé mientras montaba todo y cómo los arreglé. El primero fue un error 404 al intentar entrar a las páginas, que ocurrió porque se me olvidó conectar la carpeta de mi ordenador con la de Docker. Lo averigüé mirando dentro del contenedor con docker exec -it nimbus_apache ls -la /var/www/html, donde vi que la carpeta estaba vacía, y lo arreglé añadiendo la línea del volumen en el archivo de Docker. El segundo fallo fue que la web interna mostraba por error el contenido de la pública, algo que pasó porque a Nginx le faltaba una línea en su configuración. Me di cuenta revisando el archivo interno con docker exec -it nimbus_nginx cat /etc/nginx/conf.d/default.conf | grep proxy_set_header y lo solucioné volviendo a escribir esa línea, dejando la práctica terminada.
